# C72 — one acceptance, explain iKant, then choose mode

## New product promise (2026-10-08)
NEW first input -> pinned five-file GitHub API orientation -> full Terms/freeze -> later standalone **I ACCEPT** -> deterministic 100-variant-ranked standard explanation -> subsequent explicit CANONICAL or EXPERIMENTAL selection.

This is one Terms consent for both modes. Selecting a mode is an instruction, not a second consent. The accepted human message alone does not establish native event identity, replay resistance, runtime execution, persistence or ACTIVE.

**CANONICAL**: discouraged in unverified ChatGPT Projects. Before using C59 owner activation the real host must expose a preregistered original message hook, capture the actual acceptance event, and satisfy owner materialization, executed-provenance, durable writer and ACTIVE readback. Old automatic post-accept activation is compatibility only, not the user-facing C72 default. The blocked original event cannot be recreated at selection time.

**EXPERIMENTAL**: recommended low-assurance path. The new C72 selection receipt can be passed through the C69 preflight to C70/C71 without a *new* I ACCEPT EXPERIMENTAL. Legacy C69 callers remain supported for the existing test suite but must never be proposed in a new unified onboarding. No source-origin, actual Node, future turn routing, native delivery, persistence, mode ACTIVE or owner privilege inferred from selection alone.

## Standard human introduction
The source module host/c72-unified-mode-admission.mjs generates 100 distinct short complete versions, scores only measurable textual constraints and returns a reproducible choice. This is editorial/formal selection, not a real-world user preference study.

## Trust and migration
- Common textual receipt is self-hashed, not signed by ChatGPT. The receipt does NOT authenticate human origin, host event or chronology.
- Unchanged frozen source and Terms digest are bound across the common gate and selection. A caller asserting it presented Terms is not independent host presentation evidence.
- C72 cannot run or impersonate C59. The canonical owner remains unchanged.
- C69 legacy second-consent behavior is retained only for backward compatibility; use C72-selected EXPERIMENTAL for new entries.
- Existing C30/C31/DEGRADED diagnostic and runtime tiers keep their original meaning.
- A user without a real callable Node can read the intro and choose EXPERIMENTAL, but must see EXPERIMENTAL_SELECTED_NOT_RUNNING rather than an execution claim.
- An externally supplied current-host message source/writer/lease receipt is necessary for persistent ChatGPT-native control.

## Testing and honest qualifications
- Node 20+ tests of common consent, orientation, two modes, C69 -> C70 -> C71 reuse and negative candidates.
- A 10^6 six-axis semantic lattice checks exact consent, mode, Terms presentation, source offer, orientation integrity and forbidden authority escalation, with a separate oracle; requires zero unsafe ACTIVE and zero mismatches.
- Earlier suites for C59/C61/C64/C68 must remain conforming after migration, or deviations must be exposed and corrected before merge.
- contracts/c72-product-value-promise.json defines independent user-value acceptance at >=95% only with real holdout outcome evidence and native-host witnesses. A million semantic vectors and green CI do not prove this quantitative target.

## Open edges

2. No physical per-turn host bridge, state writer, readback or native DOCX presentation attested here.

C72 is an engineering prototype/revision, not proof of a persistent iKant instance in ChatGPT.
