# P0 — C72 bootstrap: first-turn witness and automatic transport are separate edges

## Observed incidents (25 October 2026)
- Orientation produced five visible links, but did not preserve five original `blob_sha1` identifiers. After a distinct `I ACCEPT`, the existing `reenterC72V2PostAccept` correctly rejected the reconstructed/absent `priorTurnEvidence`: `C72_ORIENTATION_WITNESS_MISSING`. Post-consent rereads do **not** prove prior observations.
- A previous attempt observed Node 22 and GitHub API separately, yet stopped at `C72_SOURCE_BRIDGE_UNKNOWN` while `planC72HostRecovery` still returned `AUTO / VERIFY_PINNED_API_TRANSPORT`. The action had not been performed to a known outcome.
- The Host incorrectly conflated engineering permissions with C72 admission in an earlier chat. A human request for repository audit/PR is HOST_ENGINEERING, not a C72 runtime message.

These are observed Host orchestration failures, not evidence that C72/v2 is missing or that the ChatGPT provider can be controlled by repository files. PR #165 limited the preaccept read budget, #167 supplied original-owner reentry, and #168 added the planner and brand-emission guard. They did **not** bind live connector responses to Node or guarantee first-turn SHA retention.

## Minimal corrective graph
```
HUMAN_FIRST_CONTACT -> HOST_ENGINEERING (explicit repository work)
                    -> ORIENTATION (all other first inputs)
ORIENTATION: ONE HEAD -> five ordered pinned direct reads with blob SHA1
            -> store + show first-turn SHA witness -> show Terms -> freeze
            -> if witness missing, STOP BEFORE inviting I ACCEPT
distinct exact I ACCEPT -> Node 20+ -> live HEAD equals pinned HEAD
            -> explicit bound GitHub read callbacks -> 5 pinned bytes
            -> original C72/v2 reentry -> validate receipt + full introduction
            -> STOP and await a further exact EDU/CANONICAL turn
```

`host/project-c72-preaccept-gate.mjs` now exports the Host witness on the **Terms-link display transition** when the gateway was already installed. A Host without the gateway must capture the same original SHA fields from the five permitted direct GitHub API reads, not invent them after the event. `distinct_human_message_observed` stays false until a genuinely later exact `I ACCEPT` is observed by the Host.

`host/project-c72-host-recovery.mjs#executeC72PostAcceptRecovery` runs **after** acceptance. In Node, `VERIFY_NODE_20` is concrete, not a generic instruction. A missing `readMain` or `readPinnedDocument` callback yields `C72_SOURCE_BRIDGE_UNBOUND` (not **UNAVAILABLE_VERIFIED**). With bound callbacks, one HEAD read and five document reads feed the **unchanged original** `reenterC72V2PostAccept`, which hashes exact bytes and invokes original C72/v2. A failed/unknown read and an unknown owner call are terminal, without blind retry. Owner receipt and introduction are validated again before success is returned. Only the existing C72 owner can issue those original receipt objects.

This runner is a repo software path, **not** a provider-native tool binding or cross-conversation persistence. No callback can be inferred from a tool catalog, a prompt, a GitHub search result, or Node availability alone. The external Host must actually pass data through a verified binding. If that cannot be observed, an honest typed STOP remains; the user is not asked to diagnose a gateway or to upload a Project bundle. The current failed consent turn is **not** retroactively repaired.

## Qualification / falsification
`tests/project-c72-recovery-10k.test.mjs` runs deterministic 10 × 10 × 10 × 10 distinct axes, mixing exact human gate, first-turn witness, Node/API binding, and source read/byte tampering. A positive traverses the original C72 receipt and validates it; negatives must stop on a typed first edge before any owner claim. JSONL + SHA-256 + reread receipt are generated by the Node 20/22 CI. These 10,000 cases are **software simulations**, not 10,000 live ChatGPT sessions. Main merge, CI green, prompt installation, native source bridge and user-visible brand presence are separate facts. `PRODUCT_NO_GO` without native integration evidence.

4. Original C72/v2 returns validated receipts and an unmodified full introduction, with no fake A voice and no preemptive EDU.
5. Explicit Host repository audit/patch/PR stays outside the iKant gate. Engineering HEAD never repins iKant.
6. Prompt source, generation contract, generator, BOOTSTRAP routing and Node 20/22 tests agree on the new path. No new original owner, native SVG/avatar or C135 writer.

## Generation matrix, propagation ownership and release process

`contracts/project-prompt-generation.json` is the canonical **generation matrix**. Its `responsibility_registry` is a source-level map of 12 routes to file/function, scope, edge, evidence and an explicit `provider_bound:false`. It is **not** a second cognitive controller. The original `scripts/build-project-oneshell-prompt.mjs` reopens the matrix from `git show HEAD`, checks semantic bounds and live exports, and reads immutable source blobs. The Project string remains `project/session-chat/PROMPT.txt`. `BOOTSTRAP.project_session` points to bootstrap owner paths; Node CI verifies alignment. If any layer disagrees, generation must fail rather than silently updating only one surface.

Minimal propagation: **owner code** → `BOOTSTRAP.project_session` route → **Project source prompt** → **generation matrix** → **canonical generator checks** → **Node 20/22 tests** → PR commit TREE/blob readback → **human merge** → new main HEAD verified → **explicit Host generation request** → byte-identical prompt and metadata. No separate manually authored portable template. The glifo stays the original source-verified SVG in the existing renderer: generation does not install that renderer in ChatGPT.

**Two epochs, not one bypass.** The Host can generate the portable prompt with one explicit human request *after merge* against the then-current main HEAD; this is **engineering only** and never requires C72, selecting EDU, or a fake prior iKant consent. By contrast, `SOURCE_LOCK` rotation of an iKant **runtime** epoch remains `EXPLICIT_REPIN_REQUIRES_FRESH_C72`, with no receipt, C87 ledger or C135 instance transfer. This PR does **not** weaken the original C72/v2 owner to disguise an old consent as a new one. Any future one-turn runtime epoch upgrade needs an independently reviewed, new original owner contract and real accepted-turn proof, and is **outside #169**.

**Release status:** a green repo CI establishes the source-level software DoD. Live API→Node native dispatch, cross-turn witness persistence, current Project installation equality, provider delivery and persistent user-visible glyph remain independent DoD, hence **PRODUCT_NO_GO** unless separately observed.
